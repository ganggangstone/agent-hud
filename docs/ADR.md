# 결정 기록 (ADR)

**왜 그렇게 정했는지**만 적는다. 무엇을 만드는지와 사용법은 `README.md`에 있다.

결정이 바뀌면 항목을 고치고 바뀐 이유를 남긴다. 지우지는 않는다. 왜 그때 그걸 안 골랐는지
잊으면 같은 논의를 처음부터 다시 하게 된다.

---

## 1. 만드는 방식

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **단일 파이썬 파일 + 표준 라이브러리** ✅ | 설치할 패키지가 없음, 의존성 취약점·버전 충돌 없음 | HTML/CSS/JS를 파이썬 문자열 안에 써야 한다(에디터 지원 없음) | **채택** |
| Flask/FastAPI | 라우팅·템플릿이 편함 | 요청 처리는 GET 5개, POST 5개뿐인데 `pip install`이 필요해진다 | 기각 |
| Electron/Tauri 데스크톱 앱 | 창·트레이가 자연스러움 | 상태를 보는 게 전부인 도구에 상주 프로세스와 수십~수백 MB를 쓴다 | 기각 |
| CLI (`agent-hud status`) | 가장 가벼움 | 상태는 작업하면서 계속 봐야 하는데 CLI로는 한 번씩 찍어볼 수만 있다. 켜고 끄기도 못 한다 | 기각 |

설치가 간단하고 브라우저에 계속 띄워둘 수 있는 건 첫 번째뿐이었다. 문자열 안의 HTML은 따옴표
하나만 잘못 들어가도 머리글만 나오고 나머지 화면이 안 그려져서 `tests/test_page_js.py`로 막는다(자세한 것은 `CONTRIBUTING.md`).

상태를 보는 CLI는 기각했지만, 그룹 적용만은 나중에 `groups`·`apply` 명령으로도 열었다. 폴더에서
작업하다 바로 적용할 때 쓰고, 서버가 떠 있지 않아도 같은 함수를 부른다.

## 2. 상태 읽기

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **설정 파일을 직접 읽는다** ✅ | 빠르고, 에이전트가 실행 중이 아니어도 되고, 자주 불러도 부담이 없음 | 도구가 파일 형식을 바꾸면 조용히 깨진다 | **채택** |
| CLI를 호출해 파싱 | 공식 인터페이스라 형식 변경에 강함 | 몇 초마다 읽을 때마다 프로그램을 새로 띄워야 한다. 출력이 사람용이라 파싱이 더 취약할 수도 있다 | 기각 |

몇 초마다 다시 읽어야 해서, 읽을 때마다 프로세스를 띄우는 비용이 가장 컸다. 대신 도구가 파일
형식을 바꾸면 깨질 수 있어서, 읽기는 전부 `read_json`을 거쳐 못 읽거나 JSON 객체가 아니면 빈
값을 돌려준다. 대시보드 전체가 죽지 않고 그 칸만 비어 보인다(`tests/test_read_json.py`).

## 3. 상태 바꾸기

**규칙: 사용자 전역 파일에는 쓰지 않는다. 프로젝트 파일에만 쓴다.**

| 대상 | 쓰는 곳 |
|---|---|
| 플러그인 on/off | `<프로젝트>/.claude/settings.local.json`의 `enabledPlugins` |
| 스킬을 다른 에이전트에 적용 | `<프로젝트>/.claude/skills/`, `<프로젝트>/.agents/skills/`에 심볼릭 링크 |
| 플러그인 밖 스킬 on/off | `<프로젝트>/.claude/settings.local.json`의 `skillOverrides` |

`settings.local.json`은 Claude Code가 만드는 개인용 설정 파일이라 커밋되지 않는다. 그래서
프로젝트마다 다르게 둬도 팀 저장소에는 섞이지 않는다.

> 처음에는 플러그인 on/off를 `claude plugin enable|disable` CLI로 했다.
> "공식 명령이 있으면 그걸 쓴다"는 판단이었는데, **그 명령은 옵션 없이 쓰면 사용자 전역 설정에 쓴다.**
> 그래서 프로젝트마다 다른 플러그인 구성을 만들 수 없었고, 화면 절반에 "이 컴퓨터 전체에
> 적용"이라고 따로 적어야 했다. `enabledPlugins`를 어느 설정 파일에나 넣을 수 있다는 것을
> 확인한 뒤(→ 10번) 프로젝트 파일에 쓰는 방식으로 바꿨다. 지금은 `-s local`을 붙이면 그 명령도
> 프로젝트에만 쓴다(Claude Code 2.1.283에서 직접 확인). 다만 한 번에 플러그인 하나라, 그룹을
> 한꺼번에 적용하는 이 도구의 방식은 그대로다.

> 2026년 9월까지는 스킬 단위 차단 스위치가 있었다. `permissions.deny`에
> `Skill(플러그인@마켓플레이스:스킬)`을 썼다. 아무 데도 없는 이름의 시험용 스킬(센티널)로 직접
> 확인해보니 두 가지를 알게 됐다(→ 10번).
> 이 형식은 Claude Code가 인식하지 않아 **호출도 막지 못했다.** 올바른 형식(`Skill(플러그인:스킬)`)도
> 호출만 막고 **스킬 목록에서는 빠지지 않아** 토큰이 줄지 않는다. 이 도구의 목적은 토큰 절감이라
> 스위치를 없앴다. 예전 버전이 쓴 `@`가 든 항목은 서버 시작과 프로젝트 등록 때 두 설정 파일에서
> 지우고 로그에 남긴다(`tests/test_stale_deny_cleanup.py`). 문서에는 스킬 하나만 끄는
> 방법으로 적혀 있었지만, 목록에서 빠지는지는 직접 돌려보고서야 알았다.
> 같은 확인에서 플러그인 밖 스킬은 `skillOverrides`로 목록에서 실제로 빠졌다(→ 10번). 그래서
> 플러그인 밖 스킬에만 스위치를 다시 달았고, 그룹을 적용할 때도 그룹에 없는 것은 끈다
> (`tests/test_skill_overrides.py`). Claude Code 2.1.283에서 사용자 스킬과 프로젝트 스킬 모두 다시 확인했다.

링크를 지울 때는 **심볼릭 링크만** 지운다. 같은 이름의 진짜 폴더가 있으면 사용자가 직접 둔
것이므로 건드리지 않는다. `tests/test_link_skill.py`가 이걸 검사한다.

## 4. 화면 갱신

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **폴링 (기본 3초, 사용자가 조절)** ✅ | 코드가 `setInterval` 한 줄. 서버가 따로 기억해 둘 것이 없고, 탭을 여러 개 열어도 문제없음 | 지연이 생기고, 아무도 안 보는 동안에도 돈다 | **채택** |
| SSE / WebSocket | 즉시 반영, 바뀐 게 없으면 조용함 | 연결 상태와 재연결, 구독자를 관리해야 한다. 읽는 게 로컬 JSON 몇 개인데 그럴 값어치가 없다 | 기각 |
| 파일 감시 | 변경 순간에만 갱신 | 의존성이 생기고(결정 1 위반), 감시 경로가 프로젝트마다 늘어난다 | 기각 |

3초 지연은 쓰면서 느껴지지 않는다. 다만 사용자가 무언가를 켜거나 끈 직후에는 다음 주기를
기다리지 않고 바로 다시 읽어, 누른 결과가 곧장 보이게 했다.

주기는 사용자가 고르거나 멈출 수 있다. 파일을 계속 읽는 도구라서, 이 서버가 CPU를 얼마나
쓰는지와 지금까지 가장 많이 쓴 메모리를 푸터에 같이 보여준다.

## 5. 상시 실행

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **launchd 서비스 + 세션 훅은 프로젝트만 등록** ✅ | 터미널·세션과 무관하게 살아 있고 죽으면 자동 재시작. 포트가 안 바뀜 | macOS 전용 패키징 | **채택** |
| 세션마다 서버 기동 | 설치가 훅 하나로 끝남 | 세션을 열고 닫을 때마다 서버가 뜨고 죽는다. 포트가 바뀌고 브라우저 탭이 계속 새로 열린다 | 기각 |
| 사용자가 수동 실행 | 가장 단순 | 계속 띄워두는 화면인데 켜는 걸 잊으면 소용이 없다 | 기각 |

`server.py`에는 macOS에서만 도는 코드가 없다. 리눅스에서는 코드를 고치지 않고
`systemd --user`로 같은 구성을 만들 수 있다.

세션 훅은 `server.py --register <경로>`를 실행한다. 서버가 이미 실행 중이면 `/api/register`로
프로젝트 경로만 알리고 끝난다. 이 확인이 없으면 터미널을 열 때마다 서버가 늘어난다.
서버가 실행 중이 아니면(launchd 서비스를 등록하지 않았거나 멈춘 경우) 훅이 서버를 새로
실행하고 브라우저 탭을 연다. launchd 서비스가 떠 있으면 이렇게 되는 일은 없다.

프로젝트 목록은 훅에만 기대지 않는다. 화면의 `+ 폴더 추가`가 같은 일을 하고, 에이전트가
하나도 안 깔린 컴퓨터에서도 동작한다. 등록한 프로젝트 안에 자기 `.claude/`나 `.agents/skills`를
가진 하위 폴더가 있으면 그것도 목록에 올린다. 훅을 심으려면 도구마다 다른 설정 파일을 이 도구가
고쳐야 하는데, 그 파일들은 각 도구의 것이라 건드리지 않는다(→ 10번).

## 6. "그룹" 개념

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **도입한다 (`modes.json`)** ✅ | "개발할 땐 이것, 영상 작업할 땐 저것"을 나눠 둘 방법이 없던 문제를 푼다 | 에이전트에 없는 개념이라 "이게 공식 기능인가?" 헷갈릴 수 있다 | **채택** |
| 에이전트에 있는 것만 보여준다 | 개념이 늘지 않음 | 그러면 이걸 만들 이유가 없다 | 기각 |

헷갈릴 여지는 문서로 줄인다. README의 개념 표에 개념마다 어느 도구의 것인지 적고, 그룹은
이 도구에만 있는 개념이라고 밝힌다.

그룹은 **플러그인과 스킬을 함께** 담고, 프로젝트에 적용한다. 적용하면 그 그룹의 스킬이
프로젝트 스킬 폴더에 연결되고 플러그인 값이 프로젝트 설정에 적힌다. 적용할 때는 **설치된
플러그인 전부에 값을 적는다.** 하나라도 빠뜨리면 그 플러그인은 전역 값을 따라가서, 끈 줄
알았던 플러그인이 켜져 있게 된다. 적용을 해제하면 그룹 스킬의 링크만 지우고 플러그인 값은
그대로 둔다.

## 7. 업데이트 알림

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **Homebrew 설치본은 버튼, git 설치본은 에이전트에게 보낼 문장 복사** ✅ | 비개발자도 누르기만 하면 된다. 파일을 바꾸는 건 brew이고 서버는 명령을 부른 뒤 새 코드로 다시 뜰 뿐이다. 코드를 고쳐 쓸 수 있는 git 설치본은 건드리지 않는다 | 서버가 `brew`를 실행하는 경로가 생긴다 | **채택 (v0.4.0)** |
| 버전 확인만, 다운로드는 수동(`git pull` 또는 `brew upgrade`) | 구현이 몇 줄 | 알림 문구에 명령어가 둘 들어가 비개발자가 따라 하기 어렵다 | 교체됨 |
| 자동 업데이트 | 사용자가 아무것도 안 해도 됨 | 사용자가 모르는 사이 코드가 바뀐다. 로컬 수정과도 충돌한다 | 기각 |
| 아무것도 안 함 | 코드 0줄 | 고친 버그가 사용자에게 가지 않는다 | 기각 |

버튼은 `server.py`가 `<접두>/Cellar/agent-hud/` 아래에 있을 때만 뜬다(`brew_prefix`). `brew update`를
먼저 부르는 건 brew가 24시간 안에 받은 탭을 다시 받지 않아서다. 업그레이드 뒤 설치된 버전이
그대로면 실패로 알리고 다시 뜨지 않는다. 다시 뜰 때는 `os.execv`로 같은 PID를 쓰므로 launchd
서비스가 끊기지 않는다. git 설치본에 복사해 주는 문장은 README의 Updating 절을 가리키고, 그 절이
있는지는 `tests/test_update_hint.py`가 본다.

확인은 **반드시 백그라운드 스레드에서만** 한다. 화면이 상태를 받아올 때마다 GitHub에 물어보게
하면 GitHub이 느린 날 대시보드 전체가 멈춘다. 확인은 하루에 한 번이고, 서버가 다시 떠도 마지막
확인에서 하루가 지나기 전에는 하지 않는다(`tests/test_update_interval.py`).

## 8. 피드백 창구

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **GitHub Issues + 이슈 폼** ✅ | 따로 운영할 서버가 없음. 공개라 중복 제보가 줄고 이미 보고된 문제를 다른 사람도 볼 수 있음 | GitHub 계정 필요 | **채택** |
| 자체 수신 폼 | 계정 불필요, 비공개 | 받는 서버를 직접 관리해야 하고, 수신 주소가 코드에 드러나, 장난 전송이 오면 주소를 바꿔 다시 배포해야 함 | 기각 |

이 도구는 코딩 에이전트를 쓰는 사람이 대상이라, GitHub 계정이 필요하다는 점이 걸림돌이 될
가능성이 낮다고 봤다.

> 처음엔 자체 폼을 만들었다. 비개발자용 도구에서 쓰던 방식을 그대로
> 가져왔는데, 그쪽은 사용자에게 계정을 요구할 수 없어서 고른 방식이었다. 이 도구 사용자에게는
> 해당하지 않았다.

작성 부담은 이슈 폼(`.github/ISSUE_TEMPLATE/feedback.yml`)으로 낮췄다. 한국어와 영어를 같이
적어두고, 드롭다운만 골라도 절반은 전달되게 했고, 버전은 대시보드 링크가 미리 채운다.

## 9. 다른 에이전트 지원

**지원한다.** 처음에는 하지 않기로 했다가 결정을 바꿨다.

**처음에 하지 않은 이유**: 이 도구가 보여주던 것(플러그인 on/off, 그룹, 당시의 스킬 차단)이
전부 Claude Code 개념이라 옮길 대상이 없었다. 설정 형식도 JSON, TOML, Markdown 규칙
파일로 갈려 한 가지 방법으로 읽을 수가 없었다.

**생각을 바꾼 이유**: 지침 파일과 스킬은 사정이 달랐다. 한 프로젝트에 `CLAUDE.md`, `AGENTS.md`,
`.clinerules`가 같이 있고, 같은 규칙이 파일마다 따로 적혀 이미 내용이 달라져 있었다. 스킬은
형식이 공개 표준이라 여러 도구가 같은 파일을 읽어서 폴더째 옮겨 쓸 수 있다(→ 10번).

**만든 것**
- **지침 파일 목록**: `CLAUDE.md`·`AGENTS.md`·`.clinerules`·`.cursor/rules/` 등 30종(`CLAUDE.md` + 목록 29종)을
  프로젝트 폴더 안에서 찾아 크기·수정 시각과 함께 보여준다. 폴더 4,000개나 300줄에서 멈추고,
  멈추면 잘렸다고 표시한다. 파일은 고치지 않는다.
- **스킬 뱃지와 체크박스**: 스킬마다 어느 에이전트가 읽을 수 있는지 뱃지로 보여주고, 못 읽는
  에이전트에도 체크박스로 연결한다.

**파일끼리 내용이 달라졌는지는 비교하지 않는다.** 겹치는 줄을 문자열로 비교하면 복사해 붙인
중복은 잡지만, 같은 규칙을 다른 문장으로 쓴 경우는 못 잡고 제목·빈 줄에서 잘못 잡는다. 이런
검사를 두면 경고가 안 떴으니 괜찮다고 믿게 된다. 그래서 파일 목록만 보여주고 비교는
사람이 한다.

**플러그인 켜기·끄기는 다른 도구로 넓히지 않는다.** 다른 도구의 플러그인은
매니페스트와 마켓플레이스가 제각각이라(→ 10번), 화면에 어느 에이전트에 적용되는지 적어 두는
것으로 대신한다.

### 그 대신 읽을 수 있는 파일이 늘었다

`/api/state?project=`의 경로는 검증하지 않는다. 그래서 `/api/content`로 읽을 수 있는 파일이
지침 파일에서 모든 `SKILL.md`와 `.claude/agents/*.md`까지 늘었다. 서버는 `127.0.0.1`에서만 요청을
받고 CORS 헤더를 보내지 않아서, 다른 사이트의 JS는 보통은 응답을 읽지 못한다. 다만 `Host` 헤더를
검사하지 않아 DNS 리바인딩으로는 이론상 읽을 수 있고, POST(플러그인 켜고 끄기, 링크 변경, Homebrew
업데이트)는 다른 사이트에서도 보낼 수 있다. 업데이트 요청으로 할 수 있는 일은 사용자의 tap에 이미
올라온 버전으로 올리고 다시 띄우는 것까지다. 둘 다 사용자가 그 사이트를 열어 두고 공격자가 프로젝트 경로를 알아야
한다. **외부 접속을 열거나 이런 요청이 실제로 보이면 `Host` 검사부터 넣는다.**

## 10. 에이전트 사이에 옮겨지는 것 (찾아보고 직접 돌려봤다)

### 스킬: 형식은 같고 찾는 폴더는 다르다

`SKILL.md` 폴더 형식은 2025년 12월 Agent Skills 표준(agentskills.io)으로 공개됐고, 40여 제품이
이 형식을 읽는다. 그래서 스킬 폴더는 고치지 않고 다른 도구로 옮길 수 있다. 다만 프로젝트 안
어느 폴더에서 스킬을 찾을지는 표준에 없어서 **도구마다 찾는 폴더가 다르다.**

| 도구 | 프로젝트 | 사용자 |
|---|---|---|
| Claude Code | `.claude/skills/` **만** | `~/.claude/skills/` |
| Codex | `.agents/skills/` | `~/.agents/skills/` |
| Cursor | `.agents/skills/`, `.cursor/skills/` (+호환 `.claude/`, `.codex/`) | 동일 |
| VS Code·Copilot | `.github/skills/`, `.claude/skills/`, `.agents/skills/` | `~/.copilot/`, `~/.claude/`, `~/.agents/` |
| Gemini CLI | `.agents/skills/`(우선), `.gemini/skills/` | `~/.agents/skills/`, `~/.gemini/skills/` |
| Antigravity (`agy`) | `.agents/skills/` (+`.agents/skills.json`에 적은 경로) | `~/.gemini/config/skills/` (`~/.agents/skills/`는 안 읽음, 직접 확인) |

**Claude Code를 뺀 다섯 도구는 `.agents/skills`를 읽고, Claude Code는 `.claude/skills`만 읽는다.**
그래서 두 폴더에 같은 스킬을 연결해 두면 여섯 도구가 모두 그 폴더를 본다. 링크를 따라 읽는지는
아래에서 다섯 도구로 확인했고, Cursor는 확인하지 못했다.

프로젝트별로 스킬을 켜고 끄는 설정은 도구마다 다르거나 아예 없다. Codex는 사용자 전역 설정만
있고, Cursor와 Copilot은 없고, Gemini CLI는 슬래시 커맨드로 작업 폴더 단위로 켜고 끌 수 있다. 모든
도구가 똑같이 하는 일은 스킬 폴더를 훑는 것 하나라서, **스킬을 프로젝트 스킬 폴더에 넣고 빼는
방식만 모든 도구에서 통한다.**

**도구마다 따로 코드를 두지 않는다.** 도구별로 다른 것은 경로 문자열 하나뿐이므로 표 한 줄이면 된다
(`SKILL_ROOTS_PROJECT`). 도구마다 코드를 따로 두면 그 사본들이 나중에 서로 달라진다.

### 심볼릭 링크를 따라가는지 직접 돌려봤다

프로젝트에 **아무 데도 없는 이름**의 센티널 스킬을 심볼릭 링크로만 넣고, 비교용으로 스킬 없는
빈 폴더(음성 대조군)를 같이 뒀다. Gemini CLI·Codex·Copilot은 로컬에서 스킬 목록을 뽑는 명령이
있어 로그인 없이 확인했고, Claude Code와 Antigravity는 모델에게 물어야 해서 로그인한 상태로 확인했다.

| 도구 | 확인 명령 | 링크만 있는 폴더 | 빈 폴더 |
|---|---|---|---|
| Claude Code | `claude -p "..."` | 나옴 | 안 나옴 |
| Gemini CLI | `gemini skills list` | 나옴 | 안 나옴 |
| Codex | `codex debug prompt-input` | 나옴 | 안 나옴 |
| Copilot | `copilot skill list` | 나옴 | 안 나옴 |
| Antigravity | `agy -p "..." --add-dir <폴더>` | 나옴 | (진짜 폴더 대조군: 나옴) |

**Cursor는 확인하지 못했다.** CLI가 npm에 없어 따로 설치 스크립트를 돌려야 했다. TypeScript와
Rust로 만든 서로 다른 도구 다섯이 모두 링크를 따라갔고, 링크를 안 따라가게 하려면 일부러 그렇게
짜야 하니 Cursor도 따라갈 가능성이 높다. 다만 직접 확인하지는 않았다.

**헷갈렸던 곳**
- **Gemini CLI는 신뢰하지 않는 폴더의 프로젝트 스킬을 통째로 건너뛴다**
  (`Skipping project agents due to untrusted folder`). 처음엔 "링크가 안 된다"고 볼 뻔했는데,
  **진짜 폴더를 넣은 대조군도 똑같이 안 잡히는 것을 보고** 신뢰 설정 때문이라는 걸 알았다.
- **센티널 이름을 프롬프트에 흘리면 그 확인은 못 쓴다.** 첫 확인에서 *"이름에 X가
  든 스킬을 나열하라"*고 물었는데, 모델은 목록에 없어도 그 이름을 뱉을 수 있다. 그 확인은
  버리고, 아무 데도 없는 이름으로 다시 했다.
- **agy는 `-p`만으로는 현재 폴더의 프로젝트 스킬을 읽지 않았다.** `--add-dir`로 폴더를 지정하자
  대조군이 잡혔다. 대조군이 비어 있는 동안에는 결론을 내지 않았다.

### 스킬을 목록에서 빼는 방법 (2026-09, 직접 돌려봤다)

토큰이 줄려면 **세션을 시작할 때 스킬 이름과 설명이 아예 들어가지 않아야** 한다. 호출만
막아서는 줄지 않는다. 위와 같은 센티널 방식으로, 조건마다 모델에게 사용 가능한 스킬 이름을 나열하게 해 비교했다.
스크립트는 `tests/manual/skill_visibility.sh`(agy 조건은 `AGY=1`, 전역 조건은 `ALLOW_GLOBAL=1`). 조건마다 한 번씩 실행했고 대화형 `/skills` 화면은
따로 확인하지 않았다. 아래 표에서 `Skill(플러그인:스킬)`, `@` 형식, 플러그인 스킬의 `skillOverrides`,
공유·로컬 우선순위, agy의 `include_only`는 스크립트에 없는 조건이라 손으로 한 번 확인했다.

**Claude Code** (대조군에서 사용자 스킬·플러그인 스킬·내장 `dataviz` 모두 목록에 있음)

| 설정 (`.claude/settings.local.json`) | 사용자·프로젝트 스킬 | 플러그인 스킬 | 호출 |
|---|---|---|---|
| `permissions.deny: ["Skill(이름)"]` | **남음** | – | 막힘 |
| `permissions.deny: ["Skill(플러그인:스킬)"]` | – | **남음** | 막힘 |
| `permissions.deny: ["Skill(플러그인@마켓플레이스:스킬)"]` | – | 남음 | **안 막힘** |
| `skillOverrides: {"이름": "off"}` | **빠짐** | – | – |
| `skillOverrides: {"스킬": "off"}` / `{"플러그인:스킬": "off"}` | – | **남음** (두 키 형식 모두) | – |
| `skillOverrides: {"이름": "user-invocable-only"}` | 빠짐 | – | – |
| `skillOverrides: {"이름": "name-only"}` | 남음 (문서상 설명만 빠짐) | – | – |
| `skillOverrides: {"dataviz": "off"}` (내장) | 빠짐 | – | – |
| 공유 `settings.json`에 `off`, 로컬에 `on` | 남음 → **로컬이 이김** | – | – |

- 플러그인 스킬을 목록에서 빼는 방법은 **플러그인을 끄는 것뿐이었다.**
- 공식 문서를 조사했을 때는 "`Skill(name)` deny는 컨텍스트에서도 뺀다"고 결론 냈다. 그건 `Bash`
  같은 도구 이름에 대한 설명을 스킬에까지 넓혀 읽은 것이었고, 직접 돌려본 결과와 달랐다.

**Antigravity (`agy`)**

| 설정 | 전역 스킬 (`~/.gemini/config/skills`) | `skills.json`으로 추가한 스킬 |
|---|---|---|
| 없음 | 남음 | – |
| 프로젝트 `.agents/skills.json`의 `entries`에 전역 경로 + `exclude` | **남음** | – |
| 같은 경로 + `include_only` (아무것도 안 맞는 패턴) | **남음** | – |
| `skills.json`으로 추가한 경로 + `exclude` | – | exclude한 것만 **빠짐** |

- 프로젝트 설정으로 **전역 스킬은 뺄 수 없다.** 전역에 두지 않고 프로젝트에 넣은 스킬만 조절된다.
- 그래서 에이전트를 가리지 않고 토큰을 줄이는 방법은 **"전역에 두지 않고, 쓰는 프로젝트에만
  넣는다"** 하나다. 모든 도구가 폴더를 훑어 스킬을 찾기 때문이다.

### "에이전트가 스킬을 조용히 건너뛴다"는 재현되지 않았다

한때 이렇게 적었다. description이 긴 어떤 스킬이 Claude Code에서 로드되지 않고, 아무 신호도
없으니 이 대시보드가 잡아줄 만하다고.

같은 스킬을 프로젝트에 넣고 다시 확인하니 정상적으로 로드됐다. 이름만 바꾼 사본, 원본
그대로의 사본, 두 사본을 한 폴더에 같이 둔 경우 모두 로드됐다. 처음에 스킬이 하나도 안 나왔던(`NONE`)
결과가 무엇 때문이었는지는 특정하지 못했다.

이름을 알려준 채로 목록을 나열하게 하면 그 결과를 믿기 어렵다. "이름에 X가 든 스킬을 전부 대라"고
물으면 있는 것을 빠뜨리기도 하고 없는 것을 지어내기도 한다. 그래서 이후 확인은 **센티널 이름을
프롬프트에 넣지 않고** 사용 가능한 스킬을 전부 나열하게 했고, 음성 대조군을 같이 뒀다.

명세 위반은 파일만 읽어도 검사할 수 있다. `name`이 폴더 이름과 다르거나, 소문자·숫자·하이픈
형식에 어긋나거나, `description`이 1024자를 넘거나 비어 있는 경우다. 다만 **명세를 어겨도
로드는 될 수 있다.** 이 컴퓨터의 스킬 60개 중 description이 1024자를 넘는 것이 하나 있었는데
정상적으로 로드됐다. 그래서 화면에는 "안 읽힘" 대신 "명세 위반"으로 표시한다.

### 서브에이전트: 대부분 그대로 옮겨진다

| 도구 | 읽는 곳 | 형식 |
|---|---|---|
| Claude Code | `.claude/agents/` | Markdown + frontmatter |
| Cursor | `.cursor/agents/` + `.claude/agents/` + `.codex/agents/` | Markdown |
| VS Code·Copilot | `.github/agents/` + `.claude/agents/` | Markdown (`.agent.md`) |
| Codex | `.codex/agents/` | **TOML** (여기만 형식이 다르다) |

`.claude/agents`에 둔 파일 하나를 이미 세 도구가 읽는다.

### 플러그인: 스킬 말고도 담긴다

플러그인은 아홉 가지를 담을 수 있다: `skills/`, `agents/`, `commands/`, `hooks/`,
`.mcp.json`, `.lsp.json`, `monitors/`, `bin/`, `settings.json`. 이 중 다른 에이전트에서도
쓸 수 있는 것은 **스킬과 서브에이전트, 그리고 설정 형식만 같은 MCP뿐**이다.

그래서 화면의 플러그인 줄에는 **스킬 말고 다른 구성 요소도 칩으로 표시한다.** `스킬 6개`만
보여주면 플러그인이 통째로 옮겨진다고 오해하기 쉽다. 훅이 든 플러그인은 훅이 옮겨지지 않는다.

플러그인이 Claude Code에만 있는 것도 아니다. Codex(`codex plugin`, `.codex-plugin/plugin.json`)와
Copilot(`copilot plugin marketplace`)에도 있다. 다만 매니페스트와 마켓플레이스가 도구마다
따로라서, **도구끼리 공통으로 옮길 수 있는 건 여전히 스킬 폴더다.**

### 플러그인 on/off는 프로젝트 단위로 둘 수 있다

공식 설정 표에서 `enabledPlugins`의 범위는 `Any file`이다. 사용자·프로젝트·로컬·관리 설정
어디에나 쓸 수 있다는 뜻이다. 직접 확인했다:

| 넣은 곳 | 결과 |
|---|---|
| `<프로젝트>/.claude/settings.json`에 켜기 (전역은 꺼짐) | 그 폴더에서만 스킬이 **보임** |
| `<프로젝트>/.claude/settings.local.json`에 켜기 | **보임** (개인용, 커밋되지 않는 파일) |
| `settings.local.json`에서 전역으로 켜진 플러그인을 끄기 | 그 폴더에서만 **사라짐** |
| 설정 없는 폴더 | 전역 값을 따름 |

이 결과를 보고 결정 3을 바꿨다.

**확인하지 못한 것**: 프로젝트 설정의 `enabledPlugins`가 워크스페이스 신뢰를 요구하는지. 문서에는
`permissions.allow`·`additionalDirectories`·`extraKnownMarketplaces`는 폴더를 신뢰한다고
승인해야 적용된다고 적혀 있고, `enabledPlugins`는 그 목록에 없다. 위 확인은 신뢰 프롬프트 없이 통과했다.

### 설치·공유는 이미 해주는 도구가 있다

`skills.sh` 레지스트리와 `npx skills` CLI가 있다. `skills add <owner/repo> -a '*'`가 여러
에이전트 디렉터리에 **기본 심볼릭 링크로** 설치하고 `skills-lock.json`으로 복원한다.
그래서 설치는 그 도구에 맡기고, 이 도구는 **묶어 둔 스킬과 플러그인을 프로젝트마다 바꿔 켜는 일**을 한다.

### 세션 시작 훅은 네 도구 모두 있다

| 도구 | 훅 | 설정 |
|---|---|---|
| Claude Code | `SessionStart` | `~/.claude/settings.json` (JSON) |
| Codex | `SessionStart` | `~/.codex/config.toml` (TOML). 저장소 안 `.codex/config.toml`에 넣으면 대화형에서 안 도는 버그가 보고돼 있다 |
| Copilot | `sessionStart` | JSON. 훅 입력에 `cwd`가 들어온다 |
| Gemini CLI | `gemini hooks` | 자체 명령. `gemini hooks migrate`로 Claude Code 훅을 가져온다 |

**그래도 훅은 두 번째 선택지다.** 훅을 심으려면 도구 네 개의 설정 파일을 편집해야 하고,
형식이 갈리며, 지울 때 무엇을 어디 넣었는지 다시 찾아야 한다. 그래서 `+ 폴더 추가`를
먼저 만들었다. 이 도구의 파일에만 쓰고, 에이전트가 설치돼
있지 않아도 되고, 목록에서 빼면 끝난다. 훅은 원하면 직접 넣는 선택 사항으로 둔다.
