# 결정 기록 (ADR)

**왜 그렇게 정했는지**만 적는다. 무엇을 만드는지와 사용법은 `README.md`에 있다.

결정이 바뀌면 항목을 고치고 바뀐 이유를 남긴다. 지우지 않는다 — "왜 그때 그걸 안 골랐는지"를
잊으면 같은 논의를 처음부터 반복한다.

---

## 1. 무엇으로 만들 것인가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **단일 파이썬 파일 + 표준 라이브러리** ✅ | 설치가 파일 복사 하나, macOS에 파이썬이 이미 있음, 의존성 취약점·버전 충돌 없음 | HTML/CSS/JS가 파이썬 문자열 안에 산다(에디터 지원 없음) | **채택** |
| Flask/FastAPI | 라우팅·템플릿이 편함 | 이 도구가 하는 일은 GET 4개, POST 6개다. 그걸 위해 `pip install`을 요구한다 | 기각 |
| Electron/Tauri 데스크톱 앱 | 창·트레이가 자연스러움 | 상태를 보는 게 전부인 도구에 상주 프로세스와 수십~수백 MB를 쓴다 | 기각 |
| CLI (`agent-hud status`) | 가장 가벼움 | 상태는 **계속 보면서 작업하는 것**이지 한 번 찍어보는 게 아니다. 토글도 불가능 | 기각 |

"설치 마찰이 낮아야 한다"와 "브라우저에 상시 띄워둔다"가 나머지를 배제했다. 문자열 안의
HTML은 실재하는 단점이라 `test_page_js.py`로 막는다 — 자세한 것은 `CONTRIBUTING.md`.

## 2. 상태를 어떻게 읽는가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **설정 파일을 직접 읽는다** ✅ | 빠르고, 에이전트가 실행 중이 아니어도 되고, 자주 불러도 부담이 없음 | 도구가 파일 형식을 바꾸면 조용히 깨진다 | **채택** |
| CLI를 호출해 파싱 | 공식 인터페이스라 형식 변경에 강함 | 프로세스 기동 비용이 폴링마다 붙는다. 출력이 사람용이라 파싱이 더 취약할 수도 있다 | 기각 |

폴링이 전제라 프로세스 기동 비용이 결정적이었다. **형식이 바뀌면 깨진다는 걸 감수한
선택이므로** 읽기는 전부 `read_json`의 기본값 폴백을 거쳐 "못 읽으면 빈 값"으로 떨어진다.
대시보드가 죽는 것보다 낫다.

## 3. 상태를 어떻게 바꾸는가

**규칙: 사용자 전역 파일에는 쓰지 않는다. 프로젝트 파일에만 쓴다.**

| 대상 | 쓰는 곳 |
|---|---|
| 플러그인 on/off | `<프로젝트>/.claude/settings.local.json`의 `enabledPlugins` |
| 스킬 차단/허용 | `<프로젝트>/.claude/settings.local.json`의 `permissions.deny` |
| 스킬을 다른 에이전트에 적용 | `<프로젝트>/.claude/skills/`, `<프로젝트>/.agents/skills/`에 심볼릭 링크 |

`settings.local.json`은 에이전트가 스스로 만드는 개인용 파일이고 커밋되지 않는다. 그래서
프로젝트마다 다르게 둘 수 있으면서 팀 저장소를 오염시키지 않는다.

> **뒤집힌 결정**: 처음에는 플러그인 on/off를 `claude plugin enable|disable` CLI로 했다.
> "공식 명령이 있으면 그걸 쓴다"는 판단이었는데, **그 명령은 사용자 전역 설정에 쓴다.**
> 그래서 프로젝트마다 다른 플러그인 구성을 만들 수 없었고, 화면 절반이 "이 컴퓨터 전체"라는
> 다른 범위를 말해야 했다. `enabledPlugins`가 어느 설정 파일에나 들어간다는 것을 확인한 뒤
> (→ 9번) 프로젝트 파일 쓰기로 바꿨다. **제약인 줄 알았던 것이 우리가 고른 수단의 성질이었다.**

링크를 지울 때는 **심볼릭 링크만** 지운다. 같은 이름의 진짜 폴더가 있으면 사용자가 직접 둔
것이므로 건드리지 않는다. `test_link_skill.py`가 이걸 검사한다.

## 4. 화면을 언제 갱신하는가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **폴링 (기본 3초, 사용자가 조절)** ✅ | 코드가 `setInterval` 한 줄. 서버는 상태가 없고, 탭을 여러 개 열어도 문제없음 | 지연이 생기고, 아무도 안 보는 동안에도 돈다 | **채택** |
| SSE / WebSocket | 즉시 반영, 유휴 시 조용함 | 연결 상태·재연결·구독자 관리가 생긴다. 읽는 게 로컬 JSON 몇 개인데 그럴 값어치가 없다 | 기각 |
| 파일 감시 | 변경 순간에만 갱신 | 의존성이 생기고(결정 1 위반), 감시 경로가 프로젝트마다 늘어난다 | 기각 |

지연은 못 느낀다. **단, 사용자가 스위치를 누른 직후에는 폴링을 멈추고 즉시 다시 읽는다** —
자기가 누른 것이 반영되는 걸 기다리게 하면 안 된다.

주기는 화면에서 1·3·10·30·60초와 멈춤 중에 고른다. 파일을 계속 읽는 도구라 **자기 비용을
감추지 않는다**: 푸터에 이 서버의 메모리와 CPU 점유율을 함께 보여준다.

## 5. 어떻게 상시 실행하는가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **launchd 서비스 + 세션 훅은 프로젝트만 등록** ✅ | 터미널·세션과 무관하게 살아 있고 죽으면 자동 재시작. 포트가 안 바뀜 | macOS 전용 패키징 | **채택** |
| 세션마다 서버 기동 | 설치가 훅 하나로 끝남 | 세션을 열고 닫을 때마다 서버가 뜨고 죽는다. 포트가 흔들리고 브라우저 탭이 계속 새로 열린다 | 기각 |
| 사용자가 수동 실행 | 가장 단순 | 상시 상태판인데 켜는 걸 잊으면 존재 의미가 없다 | 기각 |

`server.py`에 OS 종속 코드는 없다. 리눅스는 `systemd --user`로 같은 구조를 만들 수 있고
코드를 바꿀 필요는 없다.

세션 훅은 `server.py --register <경로>`를 실행한다. 서버가 이미 실행 중이면 `/api/register`로
프로젝트 경로만 알리고 끝난다. 이 확인이 없으면 터미널을 열 때마다 서버가 늘어난다.
서버가 실행 중이 아니면(launchd 서비스를 등록하지 않았거나 멈춘 경우) 훅이 서버를 새로
실행하고 브라우저 탭을 연다. launchd 서비스가 떠 있는 한 이 경로는 타지 않는다.

프로젝트 목록은 훅에만 기대지 않는다. 화면의 `+ 폴더 추가`가 같은 일을 하고, 에이전트가
하나도 안 깔린 기계에서도 동작한다 — 훅을 심으려면 도구마다 다른 설정 파일을 우리가
편집해야 하는데, 그건 남의 파일이다(→ 10번).

## 6. "그룹"이라는 개념을 도입할 것인가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **도입한다 (`modes.json`)** ✅ | 실제 문제를 푼다 — "개발할 땐 이것, 영상 작업할 땐 저것"을 표현할 방법이 없었다 | 에이전트에 없는 개념이라 "이게 공식 기능인가?" 헷갈릴 수 있다 | **채택** |
| 에이전트에 있는 것만 보여준다 | 개념이 늘지 않음 | 이 도구를 만든 동기 자체가 사라진다 | 기각 |

헷갈림은 문서와 화면 문구로 해결한다. README의 개념 절에 **Agent HUD's own addition**이라고
명시했다 — 이 문장을 지우지 말 것.

그룹은 **플러그인과 스킬을 함께** 담고, 프로젝트에 적용한다. 적용하면 그 그룹의 스킬이
프로젝트 스킬 폴더에 걸리고 플러그인 값이 프로젝트 설정에 적힌다. 적용할 때는 **설치된
플러그인 전부에 값을 명시한다** — 하나라도 빠뜨리면 전역 값을 물려받아 "왜 이게 켜져 있지"가
된다.

## 8. 피드백을 어디로 받는가

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **GitHub Issues + 이슈 폼** ✅ | 인프라 0. 공개라 중복 제보가 줄고 "알려진 문제"를 남이 볼 수 있음 | GitHub 계정 필요 | **채택** |
| 자체 수신 폼 | 계정 불필요, 비공개 | 수신 인프라를 관리해야 하고, URL이 코드에 노출돼 장난 전송 시 재배포가 필요 | 기각 |

**계정 필요라는 단점이 이 사용자층에선 비용이 아니다** — 설치가 `git clone` + 셸 스크립트 +
설정 파일 편집이다. 계정을 못 만드는 사람은 애초에 설치할 수 없다.

> **뒤집힌 결정**: 처음엔 자체 폼을 만들었다. 비개발자용 도구에서 쓰던 방식을 그대로
> 가져왔는데, **그 결정을 만든 조건(계정을 요구할 수 없는 사용자층)이 여기선 성립하지
> 않았다.** 다른 프로젝트의 결론은 그 결론을 만든 조건까지 확인하고 옮겨야 한다.

작성 부담은 이슈 폼(`.github/ISSUE_TEMPLATE/feedback.yml`)으로 낮춘다: 한/영 병기,
드롭다운으로 고르기만 해도 절반이 전달되게, 버전은 대시보드 링크가 미리 채운다.

## 9. 다른 에이전트도 지원할 것인가

**지원한다.** 처음에는 하지 않기로 했다가 뒤집었다.

**하지 않기로 했던 이유(초기)**: 이 도구가 보여주던 것(플러그인 on/off, 그룹, 스킬 차단)이
전부 Claude Code 개념이라 옮길 대상이 없었다. 설정 형식도 갈린다 — JSON, TOML, Markdown 룰
파일. 공통 파서를 만들 표준이 없었다.

**뒤집은 이유**: 지침 파일과 스킬은 사정이 다르다. 한 프로젝트가 `CLAUDE.md`, `AGENTS.md`,
`.clinerules`를 동시에 들고 있고 **같은 규칙이 파일마다 중복돼 이미 갈라져 있는** 것을
확인했다. 그리고 스킬은 형식이 공개 표준이라 폴더째 이식된다(→ 10번).

**만든 것**
- **지침 파일 통합 뷰** — `CLAUDE.md`·`AGENTS.md`·`.clinerules`·`.cursor/rules/` 등 29종을
  프로젝트 트리 전체에서 찾아 크기·수정시각과 함께 보여준다. 읽기 전용이다.
- **스킬 가시성** — 스킬마다 어느 에이전트가 볼 수 있는지 뱃지로, 그리고 못 보는 에이전트에
  적용하는 체크박스.

**드리프트 내용 대조는 하지 않는다.** 겹치는 줄을 문자열로 비교하면 복붙한 중복은 잡지만
같은 규칙을 다른 문장으로 쓴 경우를 못 잡고, 제목·빈 줄에서 오탐이 난다. **못 잡는 게 더
많은 검사는 "표시가 없으니 괜찮다"는 잘못된 안심을 준다.** 색인으로 두고 대조는 사람이 한다.

**하지 않을 것**: 플러그인·그룹·스킬 차단을 다른 도구로 확장하는 것. 대응 개념이 없다.
화면에서 어느 에이전트에 적용되는지 밝히는 편이 정직하다.

### 부수 효과: 읽을 수 있는 파일 이름이 늘었다

`/api/state?project=`는 검증되지 않으므로, 지침 파일 29종을 추가하면서 `/api/content`가
허용하는 파일 이름이 2개에서 29개로 넓어졌다. 서버는 `127.0.0.1`에만 바인딩하고 CORS 헤더가
없어 타 출처 JS가 응답을 읽지 못하므로 실제 유출 경로는 없다. **외부 바인딩을 열게 되면 이
항목을 먼저 처리해야 한다.**

## 10. 에이전트 간에 무엇이 옮겨지는가 (조사와 실측)

### 스킬 — 형식은 표준, 위치는 표준이 아니다

`SKILL.md` 폴더 규격은 2025-12 공개 표준이 됐고(agentskills.io) 40여 제품이 같은 형식을
읽는다. **변환 없이 폴더째 이식된다.** 그런데 명세가 **탐색 경로를 정하지 않는다.**

| 도구 | 프로젝트 | 사용자 |
|---|---|---|
| Claude Code | `.claude/skills/` **만** | `~/.claude/skills/` |
| Codex | `.agents/skills/` | `~/.agents/skills/` |
| Cursor | `.agents/skills/`, `.cursor/skills/` (+호환 `.claude/`, `.codex/`) | 동일 |
| VS Code·Copilot | `.github/skills/`, `.claude/skills/`, `.agents/skills/` | `~/.copilot/`, `~/.claude/`, `~/.agents/` |
| Gemini CLI | `.agents/skills/`(우선), `.gemini/skills/` | `~/.agents/skills/`, `~/.gemini/skills/` |

**`.agents/skills`로 수렴하는데 Claude Code만 그걸 읽지 않는다.** 그래서 폴더 둘
(`.claude/skills`, `.agents/skills`)에 링크를 걸면 다섯 도구가 전부 켜진다.

프로젝트별 on/off 설정은 도구마다 제각각이거나 아예 없다 — Codex는 사용자 전역만, Cursor와
Copilot은 없고, Gemini CLI는 슬래시 커맨드로 workspace 범위를 지원한다. **반면 모든 도구가
공통으로 하는 일은 폴더를 훑는 것이다.** 그래서 "스킬이 프로젝트 스킬 폴더 안에 있으면
켜짐"이 유일한 도구 공통 스위치다.

**어댑터는 만들지 않는다.** 도구별로 다른 것은 경로 문자열 하나뿐이므로 표 한 줄이면 된다
(`SKILL_ROOTS_PROJECT`). 도구마다 클래스를 두면 그게 곧 갈라질 사본이다.

### 심볼릭 링크를 따라가는가 — 실측

프로젝트에 **아무 데도 없는 이름**의 센티널 스킬을 심볼릭 링크로만 넣고, 빈 폴더를 음성
대조군으로 뒀다. 네 도구 모두 로컬에서 스킬 목록을 뽑는 명령이 있어 **결제도 로그인도 없이**
확인할 수 있었다.

| 도구 | 확인 명령 | 링크만 있는 폴더 | 빈 폴더 |
|---|---|---|---|
| Claude Code | `claude -p "..."` | 나옴 | 안 나옴 |
| Gemini CLI | `gemini skills list` | 나옴 | 안 나옴 |
| Codex | `codex debug prompt-input` | 나옴 | 안 나옴 |
| Copilot | `copilot skill list` | 나옴 | 안 나옴 |

**Cursor는 미확인** — CLI가 npm에 없어 설치 스크립트가 필요했다. 서로 다른 구현체
(TypeScript·Rust)에서 넷이 전부 따라간 점, 링크를 안 따라가려면 일부러 그렇게 써야 하는 점을
보면 될 가능성이 높지만 확인한 것은 아니다.

**함정 둘**
- **Gemini CLI는 신뢰하지 않는 폴더의 프로젝트 스킬을 통째로 건너뛴다**
  (`Skipping project agents due to untrusted folder`). 처음엔 "링크가 안 된다"고 볼 뻔했고,
  **진짜 폴더를 넣은 대조군도 똑같이 안 잡히는 것을 보고** 원인을 갈랐다.
- **센티널 이름을 프롬프트에 흘리면 검사가 검사 노릇을 못 한다.** 첫 확인에서 *"이름에 X가
  든 스킬을 나열하라"*고 물었는데, 모델은 목록에 없어도 그 이름을 뱉을 수 있다. 그 확인은
  버리고, 아무 데도 없는 이름으로 다시 했다.

### 취소된 발견: "에이전트가 스킬을 조용히 건너뛴다"

한때 이렇게 적었다 — description이 긴 어떤 스킬이 Claude Code에서 로드되지 않고, 아무 신호도
없으니 이 대시보드가 잡아줄 만하다고. **재현되지 않아 취소한다.**

같은 스킬을 프로젝트에 넣고 다시 확인하니 정상적으로 로드됐다. 이름만 바꾼 사본, 원본
그대로의 사본, 두 사본을 한 폴더에 같이 둔 경우 모두 로드됐다. 처음 관측한 `NONE`이 무엇
때문이었는지는 특정하지 못했다.

**교훈은 남는다: 모델에게 목록을 나열시키는 것은 신뢰할 만한 측정이 아니다.** "이름에 X가 든
스킬을 전부 대라"는 질문은 있는 것을 빠뜨릴 수도, 없는 것을 지어낼 수도 있다. 확인은
**아무 데도 없는 이름 + 예/아니오**로 물어야 하고, 음성 대조군이 있어야 한다.

한편 **공개 명세 위반은 파일만 읽어도 검사할 수 있다** — `name`이 폴더명과 다르거나, 형식이
어긋나거나(소문자·숫자·하이픈), `description`이 1024자를 넘거나 비어 있는 경우. 다만 **명세
위반과 로드 실패는 다른 것이다**: 이 기계의 스킬 60개 중 1024자를 넘는 것이 하나 있었지만
그건 정상적으로 로드된다. 검사를 넣는다면 "안 읽힘"이 아니라 "명세 위반"이라고 불러야 한다.

### 서브에이전트 — 대체로 이식된다

| 도구 | 읽는 곳 | 형식 |
|---|---|---|
| Claude Code | `.claude/agents/` | Markdown + frontmatter |
| Cursor | `.cursor/agents/` + `.claude/agents/` + `.codex/agents/` | Markdown |
| VS Code·Copilot | `.github/agents/` + `.claude/agents/` | Markdown (`.agent.md`) |
| Codex | `.codex/agents/` | **TOML** — 여기만 형식이 다르다 |

`.claude/agents`에 둔 파일 하나를 이미 세 도구가 읽는다.

### 플러그인 — 스킬만 담지 않는다

플러그인은 아홉 가지를 담을 수 있다: `skills/`, `agents/`, `commands/`, `hooks/`,
`.mcp.json`, `.lsp.json`, `monitors/`, `bin/`, `settings.json`. 이 중 다른 에이전트로 갈 수
있는 것은 **스킬과 서브에이전트, 그리고 형식만 공통인 MCP뿐**이다.

그래서 화면은 플러그인 줄에 **나머지 구성 요소를 칩으로 표시한다.** `스킬 6개`만 보여주면
사용자는 통째로 옮겨진다고 오해한다. 훅이 있는 플러그인은 절반만 간다.

플러그인 개념 자체는 Claude Code 전용이 아니다 — Codex(`codex plugin`, `.codex-plugin/plugin.json`)와
Copilot(`copilot plugin marketplace`)에도 있다. 다만 매니페스트와 마켓플레이스가 도구마다
따로라 **공통 단위는 여전히 스킬 폴더 하나뿐이다.**

### 플러그인 on/off는 프로젝트 단위로 둘 수 있다

`enabledPlugins`의 범위는 공식 설정 표에서 `Any file`이다 — 사용자·프로젝트·로컬·관리 설정
어디에나 쓸 수 있다. 실측으로 확인했다:

| 넣은 곳 | 결과 |
|---|---|
| `<프로젝트>/.claude/settings.json`에 켜기 (전역은 꺼짐) | 그 폴더에서만 스킬이 **보임** |
| `<프로젝트>/.claude/settings.local.json`에 켜기 | **보임** (개인용, 커밋되지 않는 파일) |
| `settings.local.json`에서 전역으로 켜진 플러그인을 끄기 | 그 폴더에서만 **사라짐** |
| 설정 없는 폴더 | 전역 값을 따름 |

이 결과가 결정 3을 뒤집었다.

**미확인**: 프로젝트 설정의 `enabledPlugins`가 워크스페이스 신뢰를 요구하는지. 문서는
`permissions.allow`·`additionalDirectories`·`extraKnownMarketplaces`가 신뢰를 기다린다고
적었고 `enabledPlugins`는 그 목록에 없다. 위 실측은 신뢰 프롬프트 없이 통과했다.

### 설치·공유는 이미 풀린 문제다

`skills.sh` 레지스트리와 `npx skills` CLI가 있다. `skills add <owner/repo> -a '*'`가 여러
에이전트 디렉터리에 **기본 심볼릭 링크로** 설치하고 `skills-lock.json`으로 복원한다.
이 도구가 채우는 자리는 설치가 아니라 **묶음 단위의 프로젝트별 전환**이다.

### 세션 시작 훅은 네 도구 모두 있다

| 도구 | 훅 | 설정 |
|---|---|---|
| Claude Code | `SessionStart` | `~/.claude/settings.json` (JSON) |
| Codex | `SessionStart` | `~/.codex/config.toml` (TOML) — 저장소 안 `.codex/config.toml`에 넣으면 대화형에서 안 도는 버그가 보고돼 있다 |
| Copilot | `sessionStart` | JSON. 훅 입력에 `cwd`가 들어온다 |
| Gemini CLI | `gemini hooks` | 자체 명령. `gemini hooks migrate`로 Claude Code 훅을 가져온다 |

**그래도 훅은 두 번째 선택지다.** 훅을 심으려면 도구 네 개의 설정 파일을 편집해야 하고,
형식이 갈리며, 지울 때 무엇을 어디 넣었는지 다시 찾아야 한다. 그래서 먼저 만든 것은
`+ 폴더 추가`다 — 우리 파일에만 쓰고, 도구가 없어도 되고, 목록에서 빼면 끝난다. 훅 자동
등록은 선택 기능으로 남긴다.
